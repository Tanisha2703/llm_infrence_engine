# 1.2 Embeddings and the vocabulary matrix

**Goal:** explain how a token id becomes a vector, what that vector means, and why the same table is
used again at the very end of the model.

## The problem
After 1.1 we have integers like `6722` for `' capital'`. The number itself is arbitrary: 6723 is not
"similar" to 6722. A neural network does arithmetic, so it needs a representation where *closeness
has meaning*.

## The embedding table
A big learned table with **one row per token**: shape `(151936, 896)`. Row 6722 is 896 decimal
numbers describing `' capital'`.

```
embedding table shape: (151936, 896) -> 136.1 M numbers
```
Looking up a token is just **picking a row**: `embed_tokens(ids)`. (Mathematically identical to
multiplying a one-hot vector by the matrix, but a lookup is far cheaper.)

The numbers are **learned during training**. Nobody chooses them. Gradient descent nudges them so
that the model predicts text better.

## "Meaning as position in space"
Each token is a point in 896-dimensional space. **Cosine similarity** measures how aligned two
vectors are (1 = same direction, 0 = unrelated, -1 = opposite). Real values from your model:

```
cosine(' Paris', ' London') = 0.384
cosine(' Paris', ' banana') = -0.036
cosine(' king',  ' queen')  = 0.626
cosine(' king',  ' apple')  = 0.075
```
Related words are closer than unrelated ones.

**Honesty note (interviewers like this):** these are the *input* embeddings, a first rough guess. They
do not know context: `bank` has one vector whether it means river or money. Context is added by
attention in the 24 layers, which produce *contextual* vectors. The famous "king - man + woman = queen"
demo is about this rough input geometry and is cherry-picked as often as not.

## The same table is used backwards (tied embeddings)
At the output, the final vector must be turned back into a score per word. That is the `lm_head`, a matrix
of shape `(896, 151936)`: one dot product between the final vector and every word's vector.

Intuition: "the output vector says what it wants the next word to look like; score each dictionary
entry by how well it matches." Using the *same* matrix for input and output (**weight tying**) is
natural, and it saves 136M parameters out of 494M (28% of the model).

In code ([model.py:172](../../src/miniserve/model.py#L172)):
`self.lm_head.weight = self.model.embed_tokens.weight`. The test
[test_lm_head_is_tied](../../tests/test_model_parity.py) checks both point to the same memory.

## Why this matters for serving
- The embedding table is **136M of the weights** to hold in memory. For tiny models the table is a big share.
- The `lm_head` multiplication costs `896 x 151,936 = 136M` multiply-adds *per generated token*. That is
  the same as a chunk of the whole transformer for this small model. (Segment 1.8 shows an easy saving.)

## Interview ladder
**Level 1: What is an embedding?**
A learned dense vector per token. The network operates on vectors, not ids, because vectors can encode
similarity.

**Level 2: How is an embedding learned? Who decides the values?**
They are ordinary parameters. Training minimizes next-token loss, and gradients flow back into the rows
used, moving the vectors so tokens used in similar contexts end up close.

**Level 2: What is weight tying and why use it?**
Input embedding and output projection share one matrix. It reduces parameters (here 136M, 28%) and works
well because both map between token space and hidden space.

**Level 3: Is the embedding of "bank" different in "river bank" vs "bank account"?**
Not at the input; it is a lookup, so it is identical. The difference arises after attention layers mix in
context. Output of each layer is a contextual representation.

**Level 3: Why is the lm_head a bottleneck in decoding for small models?**
One matrix multiply of 136M weights per token against a vocabulary of 152k. For a 0.5B model that is
over a quarter of per-token compute and memory reads. It is one reason small models don't speed up as much as
the layer count suggests.
