# 1.5 Multi-head attention and GQA

**Goal:** explain why attention is split into heads, how grouped-query attention (GQA) shrinks the KV cache
7×, and be able to compute KV-cache size for any model. That last skill comes up constantly in LLM-infra interviews.

## Why more than one head?
One attention pattern can only express one kind of relationship at a time. A token may need to
simultaneously track "which noun do I refer to", "what is the previous word", "what verb am I the subject of".
So we run several attentions **in parallel** (heads), each with its own learned Q/K/V projections, and let each specialize.

Mechanically nothing new: split the 896-dimensional vector into 14 slices of 64 (14 × 64 = 896). Each head runs the
1.3 algorithm on its own slice. Concatenate the 14 outputs (back to 896) and mix them with one more matrix, `o_proj`.

## The cost problem: the KV cache
From 1.3/1.4 we keep K and V of every past token (the KV cache, Lesson 2). Its size per token is:

```
bytes per token = layers × 2 (K and V) × kv_heads × head_dim × bytes_per_number
```
For Qwen2.5-0.5B in bf16 (2 bytes): `24 × 2 × kv_heads × 64 × 2`.

## Three designs
| Design | Heads sharing K/V | kv_heads | Idea |
|---|---|---|---|
| **MHA** (original) | none: each query head has its own K/V | 14 | best quality, biggest cache |
| **MQA** | all 14 query heads share 1 K/V | 1 | smallest cache, some quality loss |
| **GQA** (Qwen, Llama 2/3) | groups of query heads share a K/V | **2** | near-MHA quality, near-MQA cache |

Real numbers (`python examples/lesson1_demos.py 1.5`):
```
MHA (14 kv heads):  86,016 bytes/token = 84.0 KB | 1000 tokens = 82 MB  | 32 users × 2000 tok = 5.13 GB
GQA ( 2 kv heads):  12,288 bytes/token = 12.0 KB | 1000 tokens = 11.7 MB | 32 users × 2000 tok = 0.73 GB
MQA ( 1 kv head ):   6,144 bytes/token =  6.0 KB | 1000 tokens =  5.9 MB | 32 users × 2000 tok = 0.37 GB
```
The model weights are about 1 GB, so with MHA 32 concurrent users would cost 5× the model itself in cache.
**This is why GQA exists:** the cache, not the weights, decides how many users fit on a GPU.

## How GQA works
14 query heads, 2 KV heads: 14 / 2 = **7 query heads per KV head**. Query heads 0–6 all use KV head 0; heads 7–13
use KV head 1. In the code the K and V tensors are simply repeated 7 times so shapes match:
[model.py:118-121](../../src/miniserve/model.py#L118-L121)
```python
rep = c.num_heads // c.num_kv_heads        # 7
k = k.repeat_interleave(rep, dim=1)
v = v.repeat_interleave(rep, dim=1)
```
**Honest detail:** `repeat_interleave` physically copies memory, which is wasteful. Production kernels (FlashAttention,
vLLM) index the shared K/V without copying. Fine for us; note the trade-off in an interview. The *cache* stores only the 2
heads, so the saving is real where it matters.

The projections shrink too: `k_proj` outputs `2 × 64 = 128` numbers, not 896. Real shapes printed earlier:
`queries (1,5,896), keys (1,5,128), values (1,5,128)`.

## Why decode speed cares
Each decode step reads the whole KV cache of that sequence from memory (on top of the weights). Smaller cache =
fewer bytes per step = faster decode and room for more users at once.

## Interview ladder
**Level 1: Why multi-head attention?**
Parallel independent attention patterns let the model capture different relationships at once, at the same total compute as one big head.

**Level 2: What is GQA and why use it?**
Several query heads share one key/value head. It reduces KV-cache size and memory traffic by the sharing factor (7× here) with very
little quality loss, so more concurrent sequences fit and decode is faster.

**Level 2: Compute the KV cache size for Llama-3-8B (32 layers, 8 KV heads, head_dim 128, bf16) for 4k context.**
`32 × 2 × 8 × 128 × 2 = 131,072 bytes = 128 KB/token`. 4096 tokens → 512 MB per sequence. (Know how to do this on a whiteboard.)

**Level 3: Why reduce KV heads rather than query heads?**
Query heads provide compute capacity and expressiveness but their results are not stored. KV heads are what we store and re-read
every step, so that is where the memory cost is.

**Level 3: GQA changes the model architecture. Can you convert an existing MHA model to GQA?**
Yes, by mean-pooling the KV heads within each group and briefly fine-tuning ("uptraining", from the GQA paper). Not free,
but cheap compared with training from scratch.

**Level 3: Does GQA change FLOPs?**
Slightly fewer in the K/V projections, but the attention score computation is the same (still 14 query heads). The win is memory
and bandwidth, not FLOPs.
