# 1.4 The causal mask, prefill and decode

**Goal:** explain why a token may only look backwards, how that is implemented, and introduce
**prefill vs decode**, the two phases that all serving optimizations revolve around.

## The rule
Token `i` may attend only to tokens `0..i` (itself and the past). It must never see token `i+1`, `i+2`...

## Why? (two reasons, both asked in interviews)
1. **At generation time the future doesn't exist.** When predicting the next word, there is nothing after the
   last token to look at. The model must behave the same during training as at inference.
2. **It makes training efficient and honest.** Training feeds a whole sentence at once and asks the model to
   predict the next token **at every position simultaneously**. If position 3 could see position 4, it could just copy
   the answer and learn nothing. The mask makes one pass equal T separate prediction tasks.

## How it's implemented
Before softmax, set the scores for forbidden pairs to **-infinity**.
Real demo (`python examples/lesson1_demos.py 1.4`), 4 tokens:
```
mask (1 = blocked):            attention weights after masked softmax:
[[0 1 1 1]                      [[1.000 0.000 0.000 0.000]
 [0 0 1 1]                       [0.285 0.715 0.000 0.000]
 [0 0 0 1]                       [0.054 0.038 0.909 0.000]
 [0 0 0 0]]                      [0.315 0.077 0.560 0.048]]
```
**Why -inf and not 0?** `softmax` exponentiates: `exp(-inf) = 0`, so the future gets *exactly* zero weight.
A score of 0 would still give weight `exp(0) = 1`, which is not "ignored".

In our code: `is_causal=True` in [model.py:123](../../src/miniserve/model.py#L123). The fused kernel applies the
triangle for us. Each row still sums to 1 (compare the real table in segment 1.3's walkthrough).

## Key consequence: the past never changes
Because token `i` depends only on tokens `0..i`, **the keys and values of existing tokens are fixed forever**, no matter
what comes next. Adding a new token doesn't alter any earlier token's representation. (Without the mask, a new
token would change everyone else's output and nothing could be cached.) This is the second half of the KV-cache
argument, after 1.3's "only K and V are reused".

## The two phases of serving a request
Say a user sends a 500-token prompt and wants 100 tokens back.

| | **Prefill** | **Decode** |
|---|---|---|
| What | Process the whole prompt | Generate output, one token at a time |
| Tokens per forward pass | 500 at once | 1 |
| Work | One big matrix multiplication | Many small ones |
| Bottleneck | **Compute** (FLOPs) | **Memory bandwidth** (reading weights) |
| Metric it drives | **TTFT**, time to first token | **TPOT / tokens per second** |

Why decode is memory-bound: for each single new token, the GPU/CPU must stream *all* 494M weights (about
1 GB in bf16) from memory just to do a tiny amount of math on one vector. The math finishes long before the data arrives.
Processing 8 tokens in the same pass would read the same weights once, nearly for free. **That observation
powers continuous batching (Stage 3) and speculative decoding (Stage 5).** Remember it.

## Interview ladder
**Level 1: What is the causal mask and why is it needed?**
A lower-triangular mask so each token attends only to earlier tokens. Needed so training matches generation (the future doesn't
exist) and so one pass can train all positions in parallel without leaking answers.

**Level 2: How is it implemented?**
Add -inf to the attention scores above the diagonal before softmax, which makes those weights exactly zero.

**Level 2: What are prefill and decode?**
Prefill processes the whole prompt in one parallel pass and produces the first token (and the KV cache). Decode then
generates one token per pass, reusing the cache. Prefill is compute-bound, decode is memory-bound.

**Level 3: Why is decode memory-bound?**
Arithmetic intensity (FLOPs per byte read) is tiny with one token: each weight is read once and used for one
multiply-add. Hardware can do far more math per byte than that, so bandwidth, not compute, is the limit.

**Level 3: What does that imply about batching?**
Batching N sequences reuses each weight read for N tokens, so throughput rises almost N× until compute becomes the
limit. That is the entire economic case for batching in LLM serving.

**Level 3: Does the mask matter during single-token decoding with a cache?**
No mask is needed: the single new query is the last position and may legitimately see all cached keys.
